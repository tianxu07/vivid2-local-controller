# Magnetic Light II GATT and single status-query experiment

Historical status-only phase. The later source GUI integration is documented
in [Magnetic Light II integration](magnetic2.md) for 1.2.0.

Date: 2026-09-03 America/Los_Angeles (capture timestamps are UTC on September 4).
Historical phase on `feature/magnetic2`, when the public version was v1.1.0.

The user physically identified one Magnetic Light II by its disappearance and
reappearance during a power cycle. Its exact advertisement and address are
private runtime inputs; neither is recorded in this document or source/tests.
`DYMNC` is physically observed on this one unit. It is not registered as a
universal model prefix, nor does this establish older Magnetic Light support.

## Diagnostic boundary

The source-only module `chihiros.magnetic2_diagnostic` adds two operations to
this controller package, with no GUI integration or public model registration:

- `gatt`: discover the exact address/name, connect without pairing, enumerate
  metadata, validate NUS, disconnect. No characteristic/descriptor reads,
  subscriptions, or application writes.
- `status`: repeat exact identity and topology validation, subscribe only to
  the resolved NUS TX object, write exactly one fixed status packet to the
  resolved NUS RX object, capture raw notifications for five seconds, unsubscribe
  and disconnect. A failed/uncertain write is not retried or compensated.

Both reuse the existing `strict_resolve_nus`, `verify_resolved_nus`,
`serialize_gatt`, address validation and `LocalSessionLog` infrastructure.
Endpoints must belong directly to the unique NUS service, satisfy the expected
properties, and pass ambiguity/blacklist checks. No global UUID lookup or
handle-based selection is used. Handles are printed only as diagnostics.
FE59, its characteristics/descriptors, and the known DFU characteristic remain
excluded from all reads, writes and subscriptions. Service discovery only
lists their metadata. No legacy fallback, pairing, connection prelude, clock
sync, control, firmware or restoration command exists in this diagnostic.

An explicit `--live` or `--dry-run` is required. Identity has no default and is
supplied by `--address` and `--name`. Timeouts must be finite and positive;
notification collection is limited to at most ten seconds. Logs always go
under the local ignored `logs/magnetic2/` directory through the CLI. It accepts
no raw packet, channel, brightness, mode or configuration arguments.

## Why the single query was justified

The pinned [upstream builder](https://github.com/TheMicDiet/chihiros-led-control/blob/05ae7654b3d4de1df887be3827cd85dd33fe0af6/src/chihiros_led_control/commands.py#L15-L17)
identifies family `5A`, mode `04`, payload `01` as the app's device-information
request. The [protocol notes](https://github.com/TheMicDiet/chihiros-led-control/blob/05ae7654b3d4de1df887be3827cd85dd33fe0af6/docs/protocol.md#runtime-and-status-responses)
describe it as a runtime/status query. Its payload has no configuration fields.
The existing local `create_status_query((0, 2))` reproduces the reviewed frame:

```text
5A 01 06 00 02 04 01 00
```

The eight-byte frame has length field six and checksum
`01 XOR 06 XOR 00 XOR 02 XOR 04 XOR 01 = 00`.
The diagnostic validates the generated bytes, length and checksum, with a
single-packet allowlist independent of the controller's wider command set.
Prior success on another Chihiros model justified a bounded compatibility
experiment after this unit's NUS topology passed. It did not establish Magnetic
Light II semantics in advance.

| `1800` | 1 | `2A00` h2 read/write; `2A01` h4 read; `2A04` h6 read; `2AA6` h8 read |
| `1801` | 10 | `2A05` h11 indicate; CCCD `2902` h13 |
| `6e400001-b5a3-f393-e0a9-e50e24dcca9e` | 14 | RX `6e400002-b5a3-f393-e0a9-e50e24dcca9e` h15 write/write-without-response; TX `6e400003-b5a3-f393-e0a9-e50e24dcca9e` h17 notify; TX CCCD `2902` h19 |
| `FE59` (permanently blacklisted) | 20 | `8ec90003-f315-4f60-9fb8-838830daea50` h21 indicate/write; blacklisted CCCD `2902` h23 |

No additional services were reported. Phase A made zero application writes
and no subscriptions. The first launch was denied log-directory access before
any scan; the subsequent GATT-only launch completed with local permissions.

## Status outcome and limits

Phase B completed exactly one application write: the reviewed status frame.
Four notifications arrived on NUS TX, in order: mode `0A`, mode `0B`, mode `36`,
then an identical second `0B`. Both connections disconnected successfully.
No lighting, channel, schedule, RTC or other application command was sent.
No `FE` snapshot appeared within the five-second collection window.

Raw bytes, timestamps, topology and identity are retained in the ignored local
session logs. The observations are limited to this unit and this experiment:

- The first notification passes the legacy XOR check. Applying the existing
  runtime decoder yields version-field value 23 and a runtime-field value of
  511 minutes. These field meanings have not been independently validated on
  Magnetic Light II. Its RX length field also does not fit the TX length rule;
  received data is retained verbatim rather than rejected or rewritten.
- The repeated `0B` resembles fan/temperature reports described for other
  fan-equipped Chihiros lights. Those offsets would suggest zero RPM and
  24 degrees C. This is a hypothesis, not validated Magnetic Light II telemetry.
- Mode `36` remains opaque. The simple XOR interpretation does not validate
  either `0B` or `36`; do not assume their trailer uses that checksum.
- All four arrived after the write, but a single run cannot establish which
  are query-triggered and which are periodic/unsolicited.

This establishes NUS transport access and notification behavior after the
query. It does not establish WRGB channel order, brightness scaling, schedule
support, control compatibility, or unchanged physical output by observation.
No further live operation was performed.

## Reproduce in PowerShell

Enter the already physically identified unit's private values at the prompts.
Do not save them into this document, source, tests, or command examples.
Close other clients that might hold the light's Bluetooth connection.

```powershell
# Run from the repository root.
$magneticAddress = Read-Host 'Private BLE address of the identified Magnetic Light II'
$magneticName = Read-Host 'Private exact advertised name'
& .\.venv\Scripts\python.exe -u -m chihiros.magnetic2_diagnostic gatt --address $magneticAddress --name $magneticName --live
```

The status operation repeats the same topology/identity checks. Each invocation
performs one status write; it is not a passive scan:

```powershell
& .\.venv\Scripts\python.exe -u -m chihiros.magnetic2_diagnostic status --address $magneticAddress --name $magneticName --notification-seconds 5 --live
```

Replace `--live` with `--dry-run` for an offline explanation with no Bluetooth
access. Exact identity is never inferred from a prefix. No auto retry occurs
when a device is missing, topology is rejected, or an operation fails.

## Validation and source scope

187 hardware-free tests passed: all 172 existing tests plus 15 new diagnostic
tests. They cover GATT-only behavior, exact identity, missing/ambiguous/DFU
endpoints, changed topology/identity before the write, packet rejection,
notification order, silence, subscription failure, uncertain write without
retry, bounded durations, cleanup, and offline dry-run behavior.

The scanner, shared transport/protocol, Vivid II and A2 Max code, existing tests,
GUI, and version constants are unchanged. The new module is not imported by
the GUI. There was no build, release, or commit. Work stops at status research
pending the user's review before any WRGB control.
